# Public WiFi-CSI dataset audit

Audit date: 2026-07-29. This is an evidence audit of public documentation only;
no raw public dataset was downloaded for this audit. `Unknown` means the public
source did not establish the field. An unknown final-evaluation field is a
failure, not an assumption in the candidate's favour.

## Decision rule

SRASTA final evaluation needs one independently collected corpus that meets all
eight requirements in the project brief: continuous capture, packet timestamps
and sequence numbers, fall start/end and post-fall-inactivity annotations,
subject and session IDs, exact hardware configuration, a research-use licence,
enough labelled non-fall time for false-alerts-per-hour, and no recording or
subject overlap with the current SRASTA partitions. It must also satisfy the
ESP32-S3 contract: LLTF only, HT20, 128 signed int8 bytes (64 complex values),
`[imaginary, real]` order, then the fixed 52-channel amplitude mask
`6..31, 33..58`.

`Final eligible` below is therefore deliberately strict. It does not judge the
scientific value of a corpus; it decides whether that corpus may support a
SRASTA final metric. In particular, a public *paper* claiming continuous
collection is not enough when the released files and annotations cannot be
verified against the required fields.

## Evidence notes

- The CSI-Bench paper reports ESP32-S3 as a smaller 1x1, 2.4 GHz, 64-subcarrier portion of fall data, and reports 1--5-minute sessions with video annotation. It also documents the broader fall cohort as U06--U22. It does **not** by itself prove that the downloaded ESP32 fall H5 clips contain per-packet sequence numbers, releaseable onset/offset timestamps, or labelled post-fall inactivity. See the [NeurIPS paper](https://proceedings.neurips.cc/paper_files/paper/2025/file/f7c68372b3d39e8d7a093eb2edaaad87-Paper-Datasets_and_Benchmarks_Track.pdf).
- WiFall is the closest public hardware match, but its documented 104-byte/52-complex representation is a different raw-frame contract. The local source card also records missing licence and fall-event-boundary evidence; those facts block final use even if the representation is useful for self-supervised work.
- ESP-Fi HAR explicitly documents amplitude-only `[1, 950, 52]`, participant/trial naming, and CC BY 4.0, but it is ESP32-C3 and trial-based. See its [dataset section and licence](https://github.com/AutoSmartGroup/ESP-Fi-HAR).
- FallDeFi's repository labels its code MIT and links the data to a third-party file host; it does not state terms for that data. The source paper describes 10-second collection units, so they cannot supply a false-alerts-per-hour denominator without additional continuous recordings and annotations.
- UT-HAR explicitly documents a timestamp column and 90 amplitude/90 phase features. That does not make its external Google Drive archive a SRASTA-compatible or clearly licensed final-evaluation dataset.
- CSI-HAR documents Raspberry Pi 4/Nexmon and variable-length 52-column activity clips. Its accompanying paper's CC BY licence applies to the article; a separate dataset licence was not found on the repository.
- WiFi-Wild is included because it is a recent Zenodo ESP32 raw-CSI lead. The Zenodo record says its files are access-restricted and does not document an annotated fall task, so it is not a usable public fall-evaluation source today.

## Guardrails for use

1. No candidate in this audit is eligible for final SRASTA metrics. Do not convert a `No` above into a conditional `Yes` by inferring undocumented fields.
2. Do not mix Intel/HP-style 90/232-feature data, NXP 58-feature data, or raw WiFall 52-complex frames directly into the SRASTA ESP32-S3 `[time, 52]` pipeline. Any permitted transfer work needs an explicit, separately evaluated representation interface.
3. The current `data/csi-bench` source and `data/external` sources remain unmodified. The current `code/runs/srasta_fall` artifact is invalid and is not evidence in this audit.
4. The current held-out U21 data and every locked SRASTA test record remain evaluation-only. They must not influence feature choice, model selection, threshold selection, calibration, or capture-protocol acceptance thresholds.
5. A candidate marked pretraining or ablation must be named in experiment provenance, kept outside the main final test partition, and must never be used to report a SRASTA final metric.
